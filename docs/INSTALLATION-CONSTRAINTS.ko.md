# Dangol 설치·복구 경로에서 확인한 제약

이 문서는 설치 명령이 아니라 개발 기기의 기록을 바탕으로 한 구현 요구사항입니다.
다른 기기의 파티션 경계·환경 위치를 대신하지 않습니다.

## boot 기록 성공만으로 부팅이 보장되지 않음

## 읽기 전용 대상 기기 사전 점검

```sh
python3 tools/device_preflight.py --adb /path/to/adb --serial YOUR_DEVICE_SERIAL
```

선택한 기기에서 이미 root ADB가 실행 중이어야 합니다. 도구는 `adb root`나
재부팅을 실행하지 않습니다. NEXELL/dangol/s5p6818 속성, fstab 파티션 대응,
실제 sysfs eMMC·파티션 크기와 경계 및 중복을 읽습니다. 개발 기록의 p1·p3
시작 섹터도 대조합니다. 나머지 시작 위치는 범위·중복만 검사하므로 동일한
전체 파티션 표의 증명은 아닙니다. 확장 파티션 컨테이너 p4는 겹침 검사에서
제외하고 그 안의 실제 p5~p9 데이터 영역을 검사합니다.

출력에 일련번호·Wi-Fi 값은 포함하지 않습니다. 실패하면 자동 재시도하지 않고
종료 코드 2로 거부합니다. 속성이 같아도 실제 보드 실크 확인은 별도로 필요합니다.
이 도구의 단위 테스트는 합성 응답을 사용하며 아직 실제 연결 기기에서 실행하지
않았습니다. 통과는 recovery 상태·system unmount·원본 백업·환경 CRC·기록 권한을
검증하지 않으므로 곧바로 플래싱해도 된다는 뜻이 아닙니다.

## boot 읽기 길이

2026-10-05 개발 기록에서 저장된 U-Boot bootcmd가 읽는 boot 길이는
21,401,600바이트였고 당시 실제 boot는 21,868,544바이트였습니다.
읽기 길이만 늘린 새 환경을 기록한 뒤 환경 전체 readback 일치와 일반 재부팅의
`sys.boot_completed=1`을 확인했습니다. 완전 전원 차단 후 콜드 부팅은 확인하지
않았습니다. 이는 당시 기기의 결과이지 새 배포 후보의 시험 결과가 아닙니다.

`pack_boot.py`의 `uboot_read_sectors`는 생성된 이미지에 필요한 최소 512바이트
섹터 수입니다. 기존 환경의 읽기 주소·시작 섹터·길이, 커널/DTB 적재와 RAM 범위를
별도로 확인해야 합니다. 예전 길이를 하드코딩하거나 숫자 하나만 같다는 이유로
환경 전체를 교체해서는 안 됩니다. 다른 기기의 환경에는 고유 식별 정보가
있을 수 있으므로 배포용 환경 바이너리도 제공하지 않습니다.

안전한 설치 도구에 필요한 항목:

1. 대상 기기의 원본 파티션 경계 및 자기 기기의 환경 백업 확보.
2. 원본 환경 CRC와 bootcmd 구문·읽기 위치·길이의 지원 여부 확인.
3. 새 boot가 파티션과 적재 RAM 범위 안에 들어가는지 확인.
4. 필요한 경우 자기 환경의 읽기 길이만 수정하고 다른 바이트 보존·CRC 갱신.
5. 기록 후 전체 환경·boot·system 읽기 검증과 자기 백업 복원 경로 확보.
6. 현장 복구 수단이 있는 상태에서 일반 재부팅 및 콜드 부팅 확인.

현재 공개 도구는 이 전체 설치 경로를 구현하거나 실기로 검증하지 않았습니다.

[boot·환경 설치 구현](BOOT-INSTALLATION.ko.md)은 자기 백업에 한정한 dry-run-first 경로입니다. 추가 실기 시험 없이 합성 테스트만 사용하며, 일반 사용자 호환성·복원 성공을 보장하지 않습니다.

[recovery ADB system 전송 구현](SYSTEM-INSTALLATION.ko.md)은 추가됐지만 합성 테스트만 통과했습니다. 일반 사용자 설치·복원 완료를 뜻하지 않으며 boot·환경 설치를 대신하지 않습니다.
`fastboot OKAY`만으로 전체 eMMC 내용 검증을 대신하지 않습니다.

## 비공개 환경의 오프라인 읽기 길이 검사

앞 영역 백업만 있다면 환경을 먼저 별도 비공개 파일로 추출할 수 있습니다.

```sh
python3 tools/extract_boot_environment.py --preboot /private/your-device-backup/dangol-preboot.bin --preboot-sha256 YOUR_PRIVATE_PREBOOT_SHA256 --owner-boot /private/your-boot.img --output /private/owner-environment.bin
```

전체 앞 영역의 크기·예상 SHA-256, boot의 kernel/DTB 형식, 개발 기록의 고정
환경 위치(3,015,168바이트)에서 16KiB 환경 CRC·지원 bootcmd를 검사합니다.
이 위치는 자동 탐색한 값이 아니므로 다른 기기·배치를 지원한다고 해석하지 마세요.
예상 해시는 새 ADB 백업의 비공개 owner-device-record preboot 항목이나 이동 전
보존한 자기 원본 지문을 사용합니다. 기기 동일성·공장 원본을 인증하는 서명은
아닙니다. boot 파일에 파티션 전체의 0 패딩이 있으면 실제 payload의 정렬된
길이로 읽기 길이를 계산합니다.

기본값은 출력 없는 검사이고 `--apply`를 추가하면 원본을 보존한 새 호스트 파일만
만듭니다. 출력은 저장소 밖 비공개 경로여야 합니다. 환경은 여전히 MAC·일련번호를
포함할 수 있으므로 출력 파일·전체 백업·그 지문은 업로드하지 마세요. 추출 성공은
읽기 길이가 충분하다는 뜻이 아닙니다. report의 read_length_sufficient를 확인하고
필요하면 아래 준비 도구를 사용하되 기기 기록은 별도 검토가 필요합니다.

실제 보관한 2026-10-05 앞 영역 백업으로 추출·host readback·원본 불변 검사를
통과했습니다. 그 백업은 수정 전 환경이라 새 승인키 제거 후보의 필요한 길이보다
짧았고, 이를 그대로 기록하거나 부팅 시험하지 않았습니다.

```sh
python3 tools/check_boot_environment.py --environment /private/owner-environment.bin --boot-image /private/new-boot.img
```

자기 기기에서 별도로 확보한 16KiB 환경 블록만 입력합니다. 전체 eMMC 파일이나
다른 사람의 환경은 사용하지 마세요. 도구는 little-endian CRC32, 중복 없는 환경
항목, 개발 기록에서 확인된 정확한 bootcmd 구문과 읽기 길이를 검사합니다.
알 수 없는 구문은 추측하지 않고 거부합니다. 값·환경 해시·개인 식별자를 출력하지
않습니다. 종료 코드 0은 이 제한된 검사에서 읽기 길이가 충분함, 1은 부족함,
2는 형식·CRC·파일 오류입니다. boot는 Android magic과 파일 크기만 검사하므로
내용 검증에는 별도로 `audit_boot.py`가 필요합니다.

2026-10-11 실제 보관한 수정 전·후 환경과 승인키 제거 후보를 대조했습니다.
수정 후 환경의 읽기 길이는 42,712섹터, 후보에 필요한 길이는 42,704섹터였습니다.
이는 환경 백업의 검사 결과일 뿐 현재 기기 환경·RAM 배치·부팅 성공의 증거가
아닙니다. 수정·기기 기록·환경 자동 탐색은 하지 않습니다.

## 자기 환경의 새 비공개 후보 만들기

```sh
python3 tools/prepare_boot_environment.py --environment /private/owner-environment.bin --boot-image /private/new-boot.img --output /private/new-environment.bin
```

기본값은 dry-run입니다. `--apply`를 추가하면 **호스트의 새 파일만** 생성합니다.
기기 기록·환경 위치 탐색·재부팅은 하지 않습니다. 출력은 공개 저장소 밖에 두어야
하고 기존 파일을 덮어쓰지 않습니다. 다른 공개 폴더에도 넣지 마세요. Linux 파일
권한은 0600이며 Windows에서는 별도로 비공개 ACL을 유지해야 합니다.

읽기 길이가 부족할 때만 필요한 섹터 수로 늘립니다. 이미 충분하면 원본 바이트를
그대로 복사하며 길이를 줄이지 않습니다. 지원된 bootcmd의 해당 숫자와 CRC 외에
모든 바이트를 유지하고 출력 readback·원본 불변을 확인합니다. 숫자의 문자열
길이가 달라져 환경 재배치가 필요하면 거부합니다. 실패한 새 파일은 자동 삭제하지
않습니다. 환경은 여전히 개인 식별값을 포함할 수 있으므로 **업로드하지 마세요**.

2026-10-11 실제 원본 환경과 승인키 제거 boot 후보로 새 비공개 환경을 만들고
host readback 검사를 통과했습니다. 이 후보를 실기에 기록하거나 부팅하지는
않았습니다. CRC 통과·충분한 길이는 파티션 경계·RAM 안전성·boot 내용이나 복구
가능성을 증명하지 않으므로 설치 허가로 해석하지 마세요.

## recovery 이미지 형식

개발 기기에서 원본 mmcblk0p7은 67,108,864바이트 ext4 파일시스템이었으며
`recovery.kernel`, `recovery.dtb`, `ramdisk-recovery.img`가 들어 있었습니다.
Android 빌드의 일반 `recovery.img`를 그대로 이 파티션에 기록하면 안 됩니다.
부트로더의 `recovery` 이름이 p7에 대응한다고 추정해서도 안 됩니다.

## 원본 백업의 범위

2026-10-11에 실제 보관된 6개 원본 파티션 파일로 공개 `verify_backup.py`의
비공개 receipt 생성 및 재검사를 수행했고 통과했습니다. 이 결과는 읽기 및
파일 무결성 검사만 증명하며 정상 복원·전체 디스크 복구·기기 동일성을 증명하지
않습니다. receipt와 백업은 공개하지 않았습니다.

[백업 무결성 안내](BACKUP-INTEGRITY.ko.md)와 함께 사용하세요. 파티션 파일 외에
자기 기기의 파티션 앞 영역·환경 및 부트로더 복구 경로가 필요할 수 있습니다.
기존 저수준 RAM 명령은 연결 손실 기록이 있어 자동 설치의 일반 검증 수단으로
간주하지 않습니다. 오류 후 자동 재시도·재부팅은 제공하지 않습니다.
