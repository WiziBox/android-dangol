# boot·환경 설치 도구 — 실기 미검증, 사용자 위험 부담

개발 기기의 이전 포팅은 동작했지만 같은 보드 이름의 다른 기기에서 동작한다고
보장하지 않습니다. 사용자의 요청에 따라 이 새 도구에 대한 추가 실기 시험은
수행하지 않습니다. 제공된 코드·문서는 보증 없이 제공되며 사용·플래싱·복원의
판단과 위험은 사용자에게 있습니다. 개발자·기여자는 적용 라이선스와 법률이
허용하는 범위에서 손해에 대한 책임을 부담하지 않습니다. 이 고지는 실기 검증이나
제조사 바이너리 재배포 허가를 대신하지 않습니다.

## 전제와 사전 검사

이 도구는 현재 개발 기록의 **고정 배치만** 지원합니다. 자기 기기의 최신
`backup_device.py` 백업(6개 파티션, 앞 영역, 두 비공개 기록)이 있어야 합니다.
기록의 일련번호가 선택한 ADB 일련번호와 같고 모든 파티션 백업의 해시가 맞아야
합니다. 제공할 boot는 자기 원본 boot와 kernel/DTB가 정확히 같고 새 ramdisk의
제한된 키·기본 인증 검사도 통과해야 합니다. 다른 커널 포팅에는 쓰지 마세요.

root ADB가 이미 실행 중인 recovery와 recovery 표식, system·boot 미마운트가
필요합니다. 자동 recovery 진입·root 전환·unmount는 하지 않습니다. 기기 속성·
파티션 경계·블록 노드·전체 앞 영역을 자기 백업과 대조합니다. 앞 영역이 달라졌다면
즉시 거부합니다. 기존 기록을 조작하거나 검사를 끄지 마세요.

```sh
python3 tools/flash_boot.py --adb /path/to/adb --serial YOUR_SERIAL --image /private/new-boot.img --sha256 YOUR_BOOT_SHA256 --owner-backup-dir /private/your-device-backup
```

기본값은 읽기 전용 dry-run입니다. 실제 기록에는 `--apply`와
`--confirm-onsite-recovery`가 둘 다 필요합니다. 이 옵션은 현장 복구 수단이 실제로
있다는 사용자 확인이며 위험을 없애는 장치가 아닙니다. 이번 프로젝트 작업에서는
이 옵션으로 실기에 실행하지 않았습니다.

## 기록 순서와 한계

1. 자기 백업에서 환경 CRC·고정 bootcmd를 검사하고, 필요한 경우 읽기 길이만 늘린
   새 환경을 메모리에 준비합니다. 길이가 이미 충분하면 환경은 바꾸지 않습니다.
2. boot 뒤를 0으로 채워 p1의 60MiB 전체를 기록하고, 기기 전체 파티션 SHA-256과
   정확한 호스트 데이터의 SHA-256을 대조합니다. 이전 ramdisk 꼬리를 남기지 않습니다.
3. 자기 앞 영역이 여전히 그대로인지 재확인합니다.
4. 변경이 필요할 때만 사용자 eMMC의 offset 3,015,168에 환경 16KiB를 기록합니다.
   환경 readback과 앞 영역 전체의 다른 바이트가 그대로인지 확인합니다.
5. 재부팅하지 않고 결과를 반환합니다. system·recovery·userdata 기록은 하지 않습니다.

4번은 **전체 디스크 블록 노드의 특정 영역에 대한 원시 기록**입니다. 다른 위치·
크기의 환경에는 절대로 사용하지 마세요. 전원 손실·ADB 연결 중단에 원자적이지
않으며 boot만 바뀌고 환경 수정이 실패하면 부팅하지 못할 수 있습니다. 오류가 나면
부분 기록을 가정하고 재부팅·자동 재시도하지 마세요. 현장 복구와 자기 원본 백업
복원 경로가 필요합니다. 완전한 공장 복원 도구는 아닙니다.

새 ramdisk·system·커널 호환성, RAM 적재 안전성, 실제 recovery의 exec-in 동작,
콜드 부팅·사용자 데이터 호환성은 검증하지 않았습니다. 단위 테스트는 합성 응답과
축소된 호스트 이미지로 기록 순서·readback 실패 시 환경 미기록·원본 byte 보존을
확인한 것입니다. 이를 실기 성공으로 해석하지 마세요.
